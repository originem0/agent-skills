# 词族讲解视频

每支视频都先有一份脚本 `projects/<课>/script.md`。口播、讲解关系和可执行分镜写在一起，它是唯一改稿入口：

写分镜与口播（含来源自查）→ `plan` → `stills` → 按当前授权审核 → `mark` → 出片 → 读音与实际成片检查

用户明确说「脚本由你审核，我只看最终成果」「审完直接出片」时，走完整的自行审核流程：核实出处、记录审稿意见与处理结果、`plan` 和画面检查通过，随后 `mark <课> approved --by "用户授权 AI 审核"` 并出片。该授权持续适用于当前任务中的改稿和读音修正；每次修改仍要重新检查并记录指纹。不要在这些中间步骤重复要求用户确认，也不要把这项授权推及无关任务。

本文件所在目录记为 `$SKILL`，命令都写成 `python -I "$SKILL/scripts/video.py" <命令> <课>`。写稿前必读 `$SKILL/references/script_guide.md` 的讲解原则和 [分镜格式](references/storyboard_guide.md)。新稿使用 `[shot: 稳定编号]` 与 `scene` JSON，不再按每个词自动套画面块。既有稿通过导入层进入同一播放器，文件不必重写。

每段声明已有经验、本段推进、依据及对应画面。关系区分词源、现代用法、联想和对比；回扣只引用已讲关系，结尾可分镜收拢。照片、文字、图形和显式动作自由组合；不靠中文释义猜动作，不强制倾斜、卡片或持续缩放。预览、定格和编码共用 `build/film.json` 对应的编译结果。

顶部保留轻量单词导航，突出本段词、淡显此前词，回讲时可重新高亮。导航由实际讲解关系编译，长词表只显示当前附近，不提前堆满未来词，不把形近反例或单词出现次数当作家族成员和学习完成度。需要明确定位时在分镜写 `focus`。

本项目与 word-family 是一体的。写稿同时读 word-family 的 `references/teaching_principles.md`：以前知识建立日常里的意外联系，适量对照易混词根词缀，按理解难点分割，在过程中整合。HTML 可以固定，视频按材料重排路线、讲法和画面；多个合适方案之间允许随机选择，选定后预览与成片保持一致。不要把讲法种类、照片比例或每词“先图后拆”变成新模板。

用户于 2026-10-30 指定 `projects/capit/capit.mp4` 为质量基准，后续视频须超过本例。写稿、审稿和检查实际成片时读 [capit 标准示例](references/capit_benchmark.md)，对照内容丰富度、连贯性、例图与例句的启发作用、画面适切性和总结完整性。沿用其品质，按新材料定路线；自动检查通过不能替代这一判断。

## 状态规则（每一步都适用）

- 只有两档：`draft`（写过或改过）、`approved`（用户确认，或用户明确授权 AI 审核后通过）。只有 `approved` 的脚本能出片。
- 只有用户明确说"通过""按我改的出片"，才能运行 `mark <课> approved`；用户说"审一遍后直接出片"也算预先确认。
- 确认后脚本、课程、所用图片、画面及编译代码、音色或语速变化，都要按本任务授权重新检查。`build/approval.json` 记录完整输入；旧稿只有文本批准记录时也须补做审核。不要绕过或手改 `status`、`checked` 和审核记录。
- AI 审稿只在用户要求时做，用户满意就不做。

## 1. 写脚本（可以几课一起）

用户点了几课，按同一清单逐课完成。只有用户允许并行代理、且环境提供这种能力时才分工；不要依赖特定厂商或固定模型名。批量要比较实际的入口、路线、句式与画面，变化服务于理解，不按固定分类或数量配额轮换。

- [ ] 课程存在，word-family 的 `build.py` 零错误（没有就先用 word-family 做课）
- [ ] `brief <课>`：读素材（词源、可用画面与照片、每个词的触发词、时长预算）
- [ ] 读共同原则、`script_guide.md` 和标准示例，定焦点问题与实际路线，写进文件头 `spine`
- [ ] 从已知场景里选意外联系，查证必要的相似词根词缀对照；事件、数字、引语先核实，不为变化硬凑
- [ ] 给需要的节拍取图：`photo <课> search …` → 看 `_sheet.jpg` → `photo <课> pick …`，或 `photo <课> get <图片网址>` 直接下载、`shot` 截网页。只给观众在现实里见过的东西配照片，优先近几年的；没有贴切的就不用，没有配额（见 `script_guide.md` 第三节）
- [ ] 写 `projects/<课>/script.md`，用稳定 shot 编号、`{触发编号|念出的内容}`、`learn/requires/recall` 和明确节点、事件表达讲解；不要手改生成的时间轴或画面页
- [ ] 同一课需要多个版本时使用独立 `--project 版本名`，脚本的 lesson 仍指原课，后续命令沿用同一项目名
- [ ] 在关系建立、对比完成或意义转折处加入短小的过程整合，下一次回扣带上新关系
- [ ] `plan <课>`：校验关系与引用、合成语音、编译时间轨道。[错误] 改到没有，[提醒] 逐条处理；删减重复或无关内容，删掉的主词写进 `skip`，不提高语速塞内容
- [ ] 按 `script_guide.md` 第九节自查，改完再 `plan` 到干净

全部完成后运行 `status`。常规审核交付每课主线、时长、出处、脚本和试听路径，然后等用户审；自行审核授权下继续审稿和出片，交付最终成片。

## 2. 用户审改

- 用户直接改 `script.md`，或写 `>> 批注` 后说"按批注改"：逐条处理并删掉批注行 → `plan` 到干净 → 告诉用户每条怎么处理的。
- 改稿时新加的事实、事件、词源，和写稿时一样要核实：来源须打开原页（打不开的不算来源），词源先查课程素材，没有就用 `etym.py`。
- 用户说"审一遍"：按 `script_guide.md` 第十节，`review <课>` 生成审稿包 → 按授权由当前 agent 或可用的独立审稿方写 `build/review_raw.md` → `review <课> --record` → 在 `review.md` 逐条写处理结果并改稿 → `plan` 到干净。用户也可以自己拿审稿包去问任何 AI，把回复贴进 `build/review_raw.md`。
- 用户说"通过"：`mark <课> approved`。

## 3. 出片

只给 `approved` 的脚本出片；`render` 自己也会检查（状态、指纹、批注、`plan` 错误），不满足就拒绝并说明原因——照原因告诉用户，不要绕过。

- [ ] `stills <课>`：每镜头末尾一张图 + 总览 `projects/<课>/stills/_sheet.jpg`，检查出界、文字重叠、箭头、裂图。退出码 1 时改对应分镜。另看关键变化的前、中、后，不能只看末帧。制作单课时不要用模板改动掩盖脚本问题；项目维护可以修复通用模板缺陷。
- [ ] 看 `_sheet.jpg`：屏幕上只有单词、词素小注、释义、例句、引文原文、章节标题和字幕，没有和解说逐句重复的句子。
- [ ] 检查画面是否把关键关系呈现出来；按内容选择照片、静态图、文字特写或动作。有动作时抽看前、中、后的肘膝、头部、重心与接触点；检查多支视频是否仍在重复同一套构图和入场方式。
- [ ] `render <课>` → `projects/<课>/<课>.mp4`；按实际轨道检查变化前、中、后，核对完整审核输入与时长后才替换旧成片，记录输入、编译结果和 MP4 哈希。编码期间输入变化也保留旧片。
- [ ] `check <课>`：判读规则见 `script_guide.md` 第十一节。确认读错的写进文件头 `say_as`，按状态规则重新审核并 `render`。抽取实际成片画面，确认字幕、例句、常用义项和对应场景可读。
- [ ] 将实际成片与 capit 标准示例对照，在 `review.md` 记录关键维度的具体证据和超过基准的改进；重点检查启发是否持续、转折是否自然、最后是否收全已讲关系。未达到质量标准就继续完善。
- [ ] 告诉用户：成片路径、时长、`check` 结果；想先看效果可以用 `preview <课>` 生成 `build/preview.html`，浏览器直接打开（画面 + 试听音频 + 拖动条）。

## 不要做的事

- 不要编造：没有来源的年份、数字、引语、事件一律不写；词源只用课程素材或 `etym.py`。
- 没有用户确认或明确的自行审核授权，不要 `mark approved`；不要在用户没要求时额外发起 AI 审稿。
- 不要为了塞进 5 分钟把语速调到默认（+20%）以上；删节拍。
- 制作单课时不要为了"修"某一课的画面随意改共用模板或零件库；项目维护中的通用问题按实际缺陷修复并验证。
